# Backlog — mi-agenda-web MVP

Scope: a Next.js + Tailwind frontend covering both experiences described in [mi-agenda-api/docs/planning/design.md](../../../mi-agenda-api/docs/planning/design.md): the public, no-auth booking site at `/:slug`, and the authenticated admin dashboard. The backend contract it consumes is fully specified in [mi-agenda-api/docs/api/endpoints-reference.md](../../../mi-agenda-api/docs/api/endpoints-reference.md); this backlog assumes that API is already built and stable (`mi-agenda-api` v0.1.0).

Payments, WhatsApp booking, native apps, multi-location, analytics, loyalty/promotions, calendar integrations, waitlists, subscriptions, invoicing, and marketplace features are out of scope, per design.md §24. Don't build toward them speculatively. Recurring appointments are in scope — see Phase 13.

Priority: **P0** = blocks the core booking loop or admin usability, **P1** = required before calling 0.1.0 done, **P2** = can slip to 0.1.1 without breaking the MVP story.

ETAs assume Claude-Code-assisted implementation (scaffolding, boilerplate components, and API wiring generated/edited with AI assistance, then reviewed by a human) — not solo manual coding. They cover implementation + basic component/e2e tests, not design debate.

## UX reference notes

[zeeg.me/richbarber22](https://zeeg.me/richbarber22) was reviewed live (rendered with a headless browser, since it's a client-rendered SPA) as UX inspiration for the public booking flow, not as a spec — mi-agenda's domain model, copy, and branding stay our own. Observed patterns worth carrying over:

- A single centered card, capped width, on a neutral light background — this holds even on desktop; the booking flow never goes multi-column.
- Business header: circular logo/avatar, business name as the page heading, a short welcome line, and a row of contact icons (email, phone, WhatsApp).
- Each service renders as its own card: name, optional expandable notes ("Más" / "Show more"), a duration badge, and a colored CTA button that advances to that service's booking flow.
- Employee selection is conditional: this particular business has a single provider, so choosing a service goes straight to the date picker with no employee-picker screen. mi-agenda must replicate that conditional — show an employee-selection step only when a business has more than one active employee, otherwise auto-select the sole one and skip straight to date selection. This is the reference site validating design.md §22's "minimal steps" requirement in practice.
- Date picker: a month-grid calendar, days with any open slot visually distinguished from days with none, month navigation arrows, no jumping to a separate page.
- Time picker: a flat list of available start times for the selected date, with a 12h/24h display toggle and the resolved timezone shown alongside it.
- Contact step: a short form (name, email, phone) directly below the confirmed date/time, ending in one full-width confirm button. mi-agenda's version drops the "add guest emails" field (out of scope) and makes email optional rather than required, per design.md §12 and `CLAUDE.md`.
- Every step keeps a visible "back" affordance and a persistent summary of what's already been chosen (date/time, service), so the customer is never lost mid-flow.

## Phase 8 — Admin dashboard redesign (calendar-first UX)

Raised because the current admin dashboard is a multi-page nav (business, employees, services, schedules, availability, appointments, customers) built for completeness rather than speed of use, and for the people actually running a business day to day, quick reading and quick action matter more than visual polish. The full idea — one page replacing the whole nav, with peripheral modals for business/employees/services/schedules — is still speculative and not scoped; what's below is the slice that was actually designed and built: turning the appointments calendar itself into a real time grid with inline slot actions.

- ~~One page, one weekly calendar as the default view (not a separate "Appointments" tab among many)~~ — still speculative, not attempted; the sidebar nav (Negocio/Clientes/Historial, etc.) is unchanged
- ~~Peripheral action buttons around the calendar's edges open modals for the less-frequent stuff currently spread across separate pages~~ — still speculative, not attempted
- Clicking an empty time block opens a quick popup to act on that slot directly (book it, or block it off) instead of navigating to a separate page and typing exact timestamps — **done**, see below
- Clicking an existing appointment opens a quick popup with its key actions inline — **deliberately not built this way**: by the time this phase was picked up, the appointment detail page had already grown into a full-featured modal (price/payment-status editing with a dirty-state confirmation flow, WhatsApp contact, status changes with override warnings) that already exceeds what an "inline quick actions" popup would offer. Clicking an appointment opens that existing modal directly instead of a separate, more limited quick-actions surface that would need to be kept in sync with it

## Phase 13 — Recurring appointments (done)

A new admin page (`/admin/recurring-appointments`) to manage repeating series for a customer (e.g. every week on Tuesdays at 9am) — for regulars on a fixed schedule, instead of re-booking or walking in each time individually. Now in scope — see `CLAUDE.md`'s `RecurringAppointment` section — deliberately narrow: one fixed weekday, one fixed time, an interval in weeks, bounded by a required end date (at most one year out), always tied to one existing customer, staff-created only.

The open design questions from this entry's earlier draft were resolved as follows, matching `mi-agenda-api`'s own backlog:

- **Data model**: pre-generation, not on-the-fly occurrences, so a generated occurrence is a completely normal appointment that shows up in every existing view (calendar, customer history, revenue totals) with no special-casing needed on this side. Generation itself is synchronous — `mi-agenda-api`'s `GenerateRuleOccurrences` runs inline inside the create and end-date-extend requests, not on a background schedule (the first version of this used an hourly scheduler goroutine; that was reworked after review, since an always-on process works against the backend's own scale-to-zero deployment goal). `end_date`'s one-year cap is what keeps a single request's worth of generation bounded
- **Editing/cancelling**: only "one occurrence" is supported directly, via the same `PATCH /appointments/{id}` any other appointment uses — there's no "this and following" or whole-series edit for that. The one exception: shortening the rule's own `end_date` cancels whatever occurrences the rule already generated past the new date (a bug caught after this shipped — see "Built" below), since those only existed because the rule's range used to cover them. Extending `end_date` never cancels anything, only shortening it does
- **Booking limits**: not bypassed — a generated occurrence is checked against the business's day/week caps the same as any other booking, and simply skipped (not force-created) if the customer is already at their limit for that date
- **Who can create one**: any authenticated role, self-scoped the same way `POST /appointments/walk-in` is — an employee's rule is always tied to their own employee record, an admin picks any employee in their business. No new permission
- **Naming**: kept "Nueva cita recurrente" / "Crear cita recurrente", matching the existing "Agregar cita" (walk-in) naming pattern
- **Notifications**: one WhatsApp confirmation when the rule is created (if at least one occurrence generated), not one per occurrence — a series spanning a year could otherwise mean dozens of messages landing on the customer's phone at once. Each occurrence still gets its own reminder as it approaches, unchanged from any other appointment

Built:

- `src/lib/api/recurring-appointments.ts` — `createRecurringAppointment`, `listRecurringAppointments`, `updateRecurringAppointment`, all threading `end_date` and reading back the response's computed `expired`/`status`
- `/admin/recurring-appointments` page: list with employee filter (admin only) and a "hide inactive by default" toggle, a create dialog (customer search, employee, service, day of week, time, interval, start date, end date capped a year out), and per rule an "Edit" button plus (for a non-expired rule) an activate/deactivate button
- `EditRecurringAppointmentDialog` edits an existing rule's service, day of week, time, interval, and end_date — never customer or employee, which the backend never allows changing. This is also the only way to reactivate an expired rule: there's no separate action, just moving `end_date` to a date on or after today, so an expired rule's dialog shows the same amber note the list card does and opens with `end_date` defaulted a year out instead of the rule's own (already-passed) value
- An expired rule (its `end_date` in the past — computed by the backend on every read, never stored) shows an amber note on its card explaining it expired, and hides the activate/deactivate toggle (which would silently do nothing, since expired always reads as inactive regardless of the stored status) in favor of Edit
- Customer detail (`customer-detail.tsx`, both the plain page and the `@modal` intercepted route) gained a "Crear cita recurrente" button that opens the management page with that customer preset and the create dialog already open
- The calendar (`time-grid.tsx`) shows a small repeat icon on any chip generated from a recurring rule (`AppointmentListItem.recurring_appointment_id`); the appointment detail page (`appointment-detail.tsx`) shows a chip with the series' weekday/time/interval (`AppointmentDetail.recurring_appointment`)
- Verified against the live API end-to-end: creating a rule generates its occurrences immediately (no waiting on a background pass), the calendar icon and detail chip render on a generated occurrence, the hide/show-inactive toggle works, and editing a rule (service + interval) both saves and re-renders correctly — this caught a real bug during verification: the edit dialog's remount `key` was originally placed on the inner `<Dialog>` element instead of on the dialog component itself, so its form fields' `useState` never picked up the selected rule's values on open
- A second bug, reported after this shipped: shortening `end_date` left already-generated occurrences past the new date sitting on the calendar untouched. Fixed backend-side (`appointment.CancelOccurrencesBeyondEndDate` — see `mi-agenda-api`'s own backlog, including a follow-up fix there for a watermark-alignment bug the first fix introduced); the edit dialog's end-date hint (`editEndDateHint`, distinct from the create dialog's own `endDateHint`) now says moving it earlier cancels anything that falls past the new range
- A confirmation step was added on top of that: submitting the edit form no longer saves directly — it opens a second `Dialog` (`confirmEditTitle`/`confirmEditCancelsWarning`/`confirmEditFutureOnlyNote`/`confirmEditGenericNote`) summarizing what this particular save will actually do, computed by comparing the form's values against the rule's own original ones: an amber cancellation warning naming the new end date if it's being shortened, a plain note that service/day/time/interval changes only affect not-yet-generated occurrences if any of those changed, or a generic "nothing already booked changes" note otherwise. Only actually saves once that's confirmed
- A third follow-up, requested once the shortening/cancellation behavior above made it clear conflicts were silently possible: what if creating a rule collides with something already on the calendar? Generation already skipped a conflicting occurrence quietly (see `mi-agenda-api`'s own backlog); now the **create** dialog previews before committing too. Submitting it calls the new `previewRecurringAppointment` (`POST /recurring-appointments/preview`) instead of creating directly, then opens a confirmation `Dialog` showing the result: if every candidate date is free, a plain "all N appointments are free to book" note; if any aren't, an amber warning plus a bulleted list (`confirmCreateConflictItem`, one per conflicting date, e.g. "mar, 15 sept — ese horario ya está ocupado") — `<ul className="list-disc">`, not separate paragraphs, since a series could have several conflicts at once. Only the real `createRecurringAppointment` call runs once the admin confirms; cancelling from there discards the preview and returns to the form. This doesn't extend to the edit dialog's own day/time/interval/service/end_date-extension changes yet — those can still silently skip a conflicting new occurrence without a preview, a narrower version of the same gap, not yet requested

## Phase 15 — Fail-fast prerequisite guards (done)

An audit (three-agent pass across the whole admin app) found a recurring pattern: several flows let an admin fill out, or even fully submit, a form for an action already known to be impossible from data already loaded — most concretely, assigning a manually-created appointment to a professional with zero working-hours `Schedule` rows configured, which crashed the calendar (a React duplicate-key bug, fixed separately — see the `git log` for that one-off). The fix applied everywhere the audit found the same shape: the moment the UI already knows a target professional can't support the action, show an explanation instead of letting the user proceed into a doomed form.

Built:

- Calendar grid (`time-grid.tsx`/`appointments-view.tsx`): clicking an empty slot for a professional with no active schedule opens a `NoScheduleDialog` instead of the usual "Agregar cita"/"Marcar como ocupado" menu, both when an admin has that professional filtered and on a professional's own calendar. When an admin has no filter (the slot menu's own employee picker resolves who), the same check runs the moment a schedule-less professional is picked there instead, via a shared `employeeIdsWithSchedule` set already computed from the schedules the page loads regardless
- `WalkInDialog` (toolbar "Agregar cita") and the Recurring Appointments create dialog: both now filter their employee picker to active professionals only, and the moment a schedule-less one is picked, replace the rest of the form with the same explanation rather than letting service/date/time be filled in for nothing
- Recurring Appointments page gained the same page-level "add a professional/service first" gate Schedules/Availability already had (it had none — the create dialog's employee `<select>` could render with zero options and no explanation). Its conflict-preview confirm dialog also no longer lets "Create" through when literally every previewed date conflicts — previously that silently created a rule that would never generate a single appointment
- Every "pick someone to create/assign something new" dropdown (walk-in, slot-menu picker, recurring-appointment create, the services page's employee checkboxes, the Schedules/Availability admin picker) now excludes inactive professionals — read-only filter contexts (the calendar's own employee filter, History's filters) were left alone, since viewing a deactivated professional's past data is still useful there
- The employee's own Availability page (and the admin's per-employee equivalent) now explains that a schedule needs to exist before "time off" means anything, instead of silently rendering a create-block form against a schedule that doesn't exist
- `mi-agenda-api`: a new `has_schedule` field on the public `GET /businesses/{slug}` response's embedded employees (`ListEmployeeIDsWithActiveScheduleByBusiness`, one bulk query), so the public booking flow excludes a schedule-less professional from `bookableEmployees` the same way it already excludes one who doesn't offer the selected service — previously such a professional could be auto-selected (as the service's only one) and the customer would hit "no available times" on every date forever with no explanation
- The Employees page gained a confirm dialog before deactivating anyone (there was none before — a single click deactivated immediately), showing a best-effort count of their upcoming confirmed appointments and which services they're the sole active professional for, without blocking the action — still the admin's call, just no longer a blind one. Active professionals with zero schedule rows also get a small inline hint on their row now, the same "not bookable yet" nudge Services already had for a service with no professional assigned

Explicitly not done in this pass (noted so it isn't silently dropped): a distinct backend preview-skip reason for "no schedule at all" vs. "slot taken" in Recurring Appointments (the client-side employee-selection check above already prevents ever reaching that confusing state, so the backend distinction is a nice-to-have); a dedicated "create customer" flow for Recurring Appointments' zero-customers dead end.

## Phase 16 — Admin↔professional view mode (designed, not built)

An admin who's also added themselves as a professional (`Employees.addYourself`) currently has no quick way to see their own calendar/services the way that professional identity would — they'd need a second login. Investigated and confirmed **no new credentials are needed**: `GET /employees/me` already resolves by `user_id`, not by the caller's role, so it already returns real data for an admin with a linked `employees` row, today, unmodified.

What a client-side "view mode" toggle needs:

- `Session` (`session-context.tsx`) gains `employeeId: string | null`, populated by a best-effort `getCurrentEmployee()` call made for every role (today `AuthGuard` skips that call entirely for `"admin"`)
- A `viewMode` piece of state (default `"admin"`), togglable only when `session.employeeId !== null` — a small switch in `AdminNav`/the top bar, shown only in that case
- Every place that branches on raw `session.role === "admin"` to decide which component to render (not real authorization — that stays backend-enforced and untouched) reads a derived `effectiveRole` instead: `viewMode === "employee" ? "employee" : session.role`. About 15 call sites (`admin-nav.tsx`, `appointments-view.tsx`, `schedules/page.tsx`, `availability/page.tsx`, `services/page.tsx`), same mechanical change each time

No backend changes required — this only changes what an already-fully-privileged admin token chooses to display, nothing about what it's allowed to do.
